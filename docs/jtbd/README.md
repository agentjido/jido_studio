# JTBD Experience Contracts

## Purpose

These documents define the direct and simple experience for each developer job.
They are inputs to a separate research, plan, and implement cycle.

Each job is a hypothesis until evidence from real past behavior supports it.
The files must not present an assumed need as a validated customer fact.

Jido Studio is distributed from GitHub. A Hex package is not part of the current
delivery model.

## Common Contract

Each job file defines:

- a solution-free job statement;
- the functional, emotional, and social dimensions;
- Push, Pull, Anxiety, and Habit hypotheses;
- direct, indirect, do-it-yourself, and non-consumption alternatives;
- a direct path with no more than five user steps;
- explicit completion, failure, and recovery states;
- observable acceptance criteria and job metrics;
- research questions about past behavior;
- evidence and gates for the research, plan, and implement cycle.

## Cycle Rules

### Research

1. Interview developers who recently had the job circumstance.
2. Reconstruct the timeline from first thought through actual use or
   non-consumption.
3. Ask about past events. Do not ask what a person might do.
4. Record the alternatives, switching forces, emotions, and team context.
5. Use at least 10 interviews across the first research cohort.

### Plan

1. Update the job file with evidence and mark assumptions that remain.
2. Select the smallest experience that can complete the job.
3. Map each proposed change to an acceptance criterion and a job metric.
4. Reject work that does not improve job completion.

### Implement

1. Build the direct path and its recovery states.
2. Add automated tests for each acceptance criterion that code can verify.
3. Measure completion time and successful outcomes, not page views alone.
4. Compare the result with the current alternative.
5. Record what was learned before the next cycle starts.
